# C3 — 1초 refresh tick 의 실제 비용

상태: **측정 완료.** 기준 커밋 `1b57111`, macOS / Apple Silicon.
근거 항목: task 9.36 (C3). Section 7 WARNING 이 "T6 가 tag 상태 + provenance
디스크 읽기 + `git stash list` 를 매 1초 tick 마다 되살린다. many-tag 저장소에서의
비용은 측정된 적이 없다"고 적었다.

## 측정 방법

커밋 60개짜리 저장소를 tag/stash 규모만 바꿔 세 벌 만들고, OS 캐시를 데운 뒤
`repo.Status(ctx, 40)` 를 20회 돌려 평균을 냈다. 같은 실행에서 git 서브프로세스
호출을 계측해 셌다.

## 결과

| tags | stashes | Status() 1회 | git 서브프로세스 |
|---|---|---|---|
| 0 | 0 | **184.9 ms** | 13 |
| 100 | 10 | 186.3 ms | 13 |
| 500 | 50 | **194.3 ms** | 13 |

호출 내역 (세 경우 모두 동일):

```
rev-parse 5   for-each-ref 2   remote 2
branch 1      log 1            status 1   symbolic-ref 1
```

## 읽기

**WARNING 이 걱정한 축은 문제가 아니다.** tag 500개 + stash 50개가 더하는 비용은
**약 9ms**, 전체의 5%다. 호출 **수**는 규모와 무관하게 13으로 일정하다. 즉 비용은
tag/stash 데이터를 읽는 데 있지 않고 **고정된 서브프로세스 수**에 있다.

**정작 눈에 띄는 것은 기준선이다.** tag 도 stash 도 없는 저장소에서 이미 185ms다.
1초 주기에 대해 duty cycle 약 19%이고, 그 대부분은 서브프로세스 13개를 띄우는
값이다(호출당 약 14ms).

**가장 눈에 띄는 중복:** `rev-parse` 가 한 번의 refresh 에서 **5번** 불린다.

**이 수치는 하한이다.** `Status()` 는 앱의 refresh 경로 전체가 아니다. WARNING 이
지목한 provenance 디스크 읽기는 이 측정에 포함되지 않았다.

## 결정하지 않은 것

측정이 C3 의 범위다. 다음 셋은 각각 별개 결정이고 데이터가 뒷받침하는 방향만 적는다.

1. **cadence 를 늦춘다.** 1초는 레거시 값이고(`d5257bb` 이후 문제로 보고된 적 없음)
   19% duty cycle 을 정당화할 근거는 기록에 없다.
2. **호출 수를 줄인다.** `rev-parse` 5회는 한 번으로 합칠 수 있어 보인다. 규모와
   무관한 고정 비용이므로 모든 저장소에 동일하게 효과가 있다.
3. **아무것도 안 한다.** 185ms 는 1초 예산 안이고 사용자 신고도 없다.

측정이 지지하는 것은 2번이다 — cadence 를 건드리지 않고 고정 비용을 깎으며,
tag/stash 규모와 무관하게 이득이 나온다. 1번은 반응성과의 맞바꿈이라 사용자 판단이
필요하다.
