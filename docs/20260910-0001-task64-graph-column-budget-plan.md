## CEO 단계 — 범위와 전제

**전제 도전.** 감사가 지목한 네 항목 중 하나(D-003)는 이미 해결됐고, 하나(D-004의
"branches가 15칸을 잡고 대부분 `-`만 찍는다")는 **행별로는 참이지만 최대값 기준으로는
거짓**이다. 이 저장소의 최대 decoration 폭이 정확히 14로 예산과 같다. 즉 branches를
줄이면 실제 내용이 잘린다.

**남는 진짜 문제:** 100컬럼 미만에서 title 가용폭이 음수다. 사용자가 보는 증상은
Reddit 피드백의 "제목이 강제로 잘린다"이고, 40컬럼에서는 제목이 아예 렌더되지 않는다.

**아무것도 안 하면?** 11.9(yymmdd 컬럼)가 영구히 막힌다. 넣을 폭이 음수이기 때문이다.

**자동결정 (P1 완결성 + P2 blast radius):** 범위는 state와 topology 두 컬럼의 적응화로
한정한다. branches는 측정이 반대를 말하므로 건드리지 않고, 그 근거를 문서에 남긴다.
D-015(범례)와 D-017(머지 커넥터 행)은 같은 파일이지만 별개 결정이므로 아래 "NOT in
scope"로 뺀다.

## Design 단계 — 적응 범위를 무엇으로 잡을 것인가

핵심 설계 갈림길은 "보이는 창(window) 기준이냐, 그래프 전체 기준이냐"다.

| | window 적응 | **graph 전체 적응** |
|---|---|---|
| 회수량 | 더 큼 (선형 구간에서 topo 1칸까지) | 14칸 고정 |
| 스크롤 | **행마다 컬럼이 재배치돼 흔들린다** | 안정 |
| 예측 가능성 | 낮음 | 높음 |

**자동결정 (P5 explicit over clever + design for trust):** graph 전체 기준.
스크롤할 때마다 레이아웃이 리플로우되는 화면은 사용자가 위치를 잃는다. DESIGN.md의
"Precise, quiet"와 어긋나고, 회수량 차이는 이 저장소에서 topo 4 대 1, 즉 3칸이다.
안정성이 3칸보다 값지다.

**적응 규칙:**

```
state 컬럼   그래프 전체에 stash/tag 를 가진 행이 하나도 없으면 폭 0 (구분자 포함 6칸 회수)
topology     그래프 전체의 최대 graph-cell 폭. 현재 공식을 상한으로, 1을 하한으로.
branches     변경 없음. 측정이 예산을 다 쓴다고 말한다.
title        나머지 전부 (기존 계약 유지)
```

**적용 후 예상:**

| 터미널 | 현재 title | 적응 후 (이 저장소) |
|---|---|---|
| 40 | -25 | -11 |
| 60 | -14 | 0 |
| 80 | -2 | **+12** |
| 100 | +9 | +23 |
| 120 | +21 | +35 |

40컬럼은 여전히 음수다. 컬럼 4개와 제목이 40컬럼에 들어가지 않는 것은 예산 문제가
아니라 물리적 한계이고, 10.10의 클램프가 이미 프레임 파손은 막는다.

## Eng 단계 — 어디를 건드리나

| 파일 | 변경 |
|---|---|
| `graph_render_format.go` `graphRowFixedWidth` | 상수 대신 측정된 폭을 받는다 |
| `graph_render_format.go` `graphTopologyWidth` | 상한으로만 쓰고, 실제 최대 lane 폭과 min |
| `view_projection.go` `GraphProjection` | 측정 결과를 실어 나른다 (`Handshake` 관습) |
| `view_graph.go` | 측정은 rows 전체에서 1회, 렌더 루프 밖 |
| `graph_render.go` 두 렌더러 | 폭을 인자로 받는다 |

**측정은 렌더 루프 밖에서 1회.** 행마다 재계산하면 O(rows²)가 되고, 더 중요하게는
행마다 다른 폭이 나와 정렬이 깨진다.

**계약 위험 (Eng 자동결정, P1):** `graphRowFixedWidth`가 지금 상수를 반환하므로
테스트가 그 값을 고정하고 있을 수 있다. 변경 시 함께 갱신하고, **폭이 달라져도 모든
행이 같은 폭을 쓴다**는 정렬 불변식을 테스트로 추가한다. 오늘 밤 두 번 나온
"한쪽 경로만 고침"을 피하려면 raw/non-raw 두 렌더러와 헤더(`renderGraphHeader`)가
같은 폭을 받아야 한다.

## DX 단계

새 의존성·새 산출물 없음. 개발자가 겪는 변화는 렌더 함수 시그니처에 폭 인자가 하나
느는 것뿐이고, 이미 `graphRowMarks`로 인자를 묶어둔 자리에 얹는다.

## 완료 기준

1. 100컬럼에서 title 가용폭이 80컬럼 대비 증가한다 (기존 6.4 기준 유지).
2. **80컬럼에서 title 가용폭이 양수다.** (신규 — 지금 -2)
3. stash/tag가 없는 저장소에서 state 컬럼이 0폭이다.
4. topology 폭이 그래프의 실제 최대 lane 폭을 넘지 않는다.
5. 모든 행이 같은 컬럼 폭을 쓴다 (정렬 불변식). 헤더 포함.
6. raw/non-raw 두 렌더러가 같은 폭을 받는다.
7. `scripts/check` CLEAN.

## 11.9 와의 관계

이 작업이 닫히면 11.9의 선행 조건이 사라진다. 80컬럼에서 +12가 확보되므로 `yymmdd`
6칸 + 구분자 1칸을 넣고도 title에 5칸이 남는다. 다만 그 5칸이 쓸모 있는지는 11.9가
따로 판단할 문제이고, 이 문서는 폭을 만들어 주는 데까지만 책임진다.
