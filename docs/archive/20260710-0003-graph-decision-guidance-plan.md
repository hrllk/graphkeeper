## 문제 정의
이 TUI는 저장소 형상을 관리하는 사람을 위한 도구다. 단순히 `git graph` 를 예쁘게 보여주는 것이 아니라, 지금 보이는 graph 를 읽고 다음 행동을 판단하게 도와야 한다.

이 제품의 사용자는 두 층위다.

- 형상을 직접 다루는 담당자
- 그 담당자에게 형상관리 방법을 배우는 부사수

둘 다 같은 화면을 봐야 한다. 하지만 원하는 결과는 조금 다르다. 담당자는 빠르게 결론을 내려야 하고, 부사수는 왜 그런 결론이 나오는지 배워야 한다.

지금 제품은 이미 다음을 할 수 있다.

- branch, remote, tag, stash 상태를 보여준다
- merge / rebase 진입점을 제공한다
- graph 상의 상태를 compact marker 로 보여준다
- tag 와 stash 를 graph 와 연결한다

다음 단계는 상태 표시를 넘어서, graph 를 읽는 판단을 돕는 것이다.

즉, 이 툴이 답해야 하는 질문은 다음과 같다.

- 이 commit 은 fast-forward(FF) 가능한가?
- 지금 이 히스토리는 이미 갈라졌는가?
- 바로 merge 할지, merge branch 를 만들어 여러 사람을 연결할지?
- 그 판단을 graph 에서 무엇으로 읽어야 하는가?

중요한 경계는 하나다. 도구가 최종 판단을 대신하지는 않는다. 도구는 판단을 돕고, 최종 판단은 사람이 한다.

## 이 제품이 멋진 이유
이 제품은 형상관리 감각을 화면 위에서 가르칠 수 있다.

숙련된 담당자는 graph 를 보고 빠르게 판단한다. 이 툴은 그 판단을 더 빠르고 안정적으로 만들어야 한다.

부사수는 그 판단을 아직 못한다. 이 툴은 다음을 같은 화면에서 보여줘야 한다.

- graph 구조가 어떻게 갈라졌는지
- FF 가 가능한지 아닌지
- 지금은 바로 merge 해도 되는지
- 아니면 merge branch 를 만들어서 담당자들을 연결해야 하는지

이게 잘 되면, 이 툴은 Git 조작 도구가 아니라 형상관리 교육 도구가 된다.

## 제약
- 최종 판단은 사람에게 남긴다.
- conflict resolution 은 하지 않는다.
- 기존 `Graph / Local / Remote / Tags` 구조를 유지한다.
- graph 는 좁은 터미널에서도 읽혀야 한다.
- compact marker 와 detail panel 의 역할을 분리한다.
- 교육용 문구는 짧고, 실제 repo 상태와 바로 연결돼야 한다.
- 기존 merge / rebase 판단 로직은 재사용하고, 새 데이터 모델은 최소화한다.

## 전제
1. 이 제품의 중심은 자동화가 아니라 판단 보조다.
2. graph 는 실제 저장소 위에서 볼 때 가장 잘 배운다.
3. FF 가능 여부, divergence, merge branch 필요성은 이미 있는 repo 상태로 설명할 수 있다.
4. 가장 좋은 흐름은 "graph 보기 -> 추천 읽기 -> 이유 이해하기" 이다.
5. 부사수 교육은 별도 모드보다 실제 사용 화면에서 설명을 붙이는 편이 낫다.

### 접근 A: 짧은 판단 배너
요약: Graph 상단이나 detail panel 에 "FF 가능", "히스토리 분기됨", "merge branch 필요" 같은 짧은 판단 문구를 보여준다.

공수: S
위험: 낮음
장점:
- 기존 Graph 구조에 가장 적게 손댄다.
- 지금 있는 merge / rebase 판단 로직을 그대로 재사용하기 쉽다.
- 숙련자에게는 빠르고, 부사수에게도 기본 결론은 전달된다.
단점:
- 왜 그런 판단이 나왔는지 배우기엔 설명량이 부족할 수 있다.
- 제품이 status indicator 처럼 보일 위험이 있다.
- "merge now" 와 "merge branch 를 만들어 연결" 의 차이가 충분히 드러나지 않을 수 있다.
재사용:
- Graph state checks
- detail panel
- action help rendering

### 접근 B: 안내형 decision panel
요약: Graph 안에 별도의 guidance block 을 두고, 현재 history shape 를 몇 개의 상태로 분류해 짧게 설명한다. 필요하면 다음 행동도 같이 제안한다.

공수: M
위험: 중간
장점:
- FF, divergence, coordination 판단을 실제로 가르칠 수 있다.
- 담당자와 부사수가 같은 화면을 보고 다른 수준으로 이해할 수 있다.
- 기존 Graph 구조와 잘 맞는다.
단점:
- 문구 설계가 필요해서 배너보다 손이 더 간다.
- 폭이 좁을 때 레이아웃 관리가 필요하다.
- 과하면 장황해질 수 있다.
재사용:
- Graph detail / action split
- merge / rebase eligibility logic
- 현재 repo status 필드

### 접근 C: 시나리오 교육 모드
요약: 시니어가 예시 branch 에 주석을 달고, 부사수에게 graph 읽는 법을 단계적으로 설명하는 교육 모드를 만든다.

공수: L
위험: 높음
장점:
- 부사수 교육에는 가장 강하다.
- 반복 교육용 예시를 남길 수 있다.
- 이 제품을 단순 툴이 아니라 코칭 도구로 만들 수 있다.
단점:
- 첫 단계로는 범위가 크다.
- 저장, 관리, 공유 방식까지 추가로 결정해야 한다.
- 현재 운영 흐름에서 너무 멀어질 수 있다.
재사용:
- Graph focus / selection model
- detail panel concepts
- hidden hotkey drawer patterns

## 권장안
**접근 B: 안내형 decision panel** 을 권장한다.

이유는 분명하다. 이 제품은 사람을 대체하는 도구가 아니라, 사람이 graph 를 읽는 능력을 더 좋게 만드는 도구여야 한다. 동시에 부사수가 봐도 이해할 수 있어야 한다. B 안은 이 두 요구를 동시에 만족시킨다.

접근 A 는 너무 얇다. 결론은 보여주지만 교육성이 약하다.
접근 C 는 좋은 미래 확장일 수 있지만, 지금은 핵심 판단 vocabulary 를 먼저 단단하게 만드는 편이 맞다.

## 열린 질문
- "merge branch 를 만든다" 는 판단을 언제 드러낼 것인가?
- FF 판단 문구를 Git 용어 중심으로 쓸 것인가, 아니면 history shape 중심으로 쓸 것인가?
- 숙련자와 부사수에게 같은 문구를 보여줄 것인가, 아니면 교육용 톤을 따로 둘 것인가?
- guidance panel 은 정보만 줄 것인가, 아니면 바로 다음 행동까지 제안할 것인가?

## 성공 기준
- 담당자가 graph 만 보고 FF 가능 여부를 말할 수 있다.
- 도구가 현재 히스토리가 안전한지, 갈라졌는지, coordination 이 필요한지 설명할 수 있다.
- 부사수가 설명을 듣고 나서 같은 상황을 다시 말로 풀어낼 수 있다.
- 좁은 터미널에서도 graph 가 읽힌다.
- 숙련자는 여전히 빠르게 조작할 수 있다.

## 배포 계획
이 기능은 기존 TUI 바이너리 안에서 배포한다. 별도 패키지나 서비스는 필요하지 않다.

기존 build / release 흐름을 그대로 사용하면 된다.

## 다음 작업
1. Graph 가 보여줘야 하는 decision state 를 정확히 정의한다.
2. 각 decision state 가 어떤 repo data 에서 나오는지 정리한다.
3. 상태별 설명 문구를 짧게 쓴다.
4. 문구와 폭 처리에 대한 테스트를 추가한다.
5. 담당자 1명과 부사수 1명에게 실제 repo 로 시험한다.

## 다음 과제
이 저장소나 가까운 저장소에서 실제 branch 세 개를 골라서, 한 명의 시니어와 한 명의 부사수에게 보여줘라. 설명은 먼저 하지 말고, 먼저 "fast-forward / merge now / merge branch and coordinate" 중 무엇으로 판단하는지 말하게 하라. 그들이 멈추는 지점과, 결국 설명을 완성할 때 쓰는 정확한 표현을 기록해라.

## 내가 본 당신의 사고 방식
- 당신은 계속 "graph 를 이해" 하는 쪽을 핵심으로 잡았다.
- 당신은 `도구는 판단을 돕고, 최종 판단은 사람이 한다` 는 경계를 분명히 했다.
- 당신은 제품을 혼자 쓰는 도구가 아니라 교육용 도구로도 보았다.
- 당신은 merge 를 단순 실행이 아니라 담당자 연결 방식까지 포함한 형상관리 문제로 봤다.
